# 内置 SOP 清单 v1 设计

状态：提案，尚未实现。日期：2026-10-30。对应[独立实施计划](../../plan/feature-builtin-sop-catalog-1.md)。本轮先纳入设计，后续通过独立功能PR实施，不在本次文档PR里增加前端代码。

7份内置内容的完整基准见[详细流程规范](builtin-sop-procedures-v1.md)：逐条定义适用/前置条件、稳定步骤ID及依赖、预期证据、停止条件、失败处理和验收标准。本文负责入口/模型/API，详细规范负责实际手册内容；后续JSON必须保持两者一致。

## 1. 产品范围

增加一个独立的“SOP”入口，首期提供内置流程的列表与详情浏览。用户可以知道Lake提供哪些标准流程、适用场景、前置条件、执行步骤、停止条件和验收方法。列表来自随应用发布的内置目录，不读取用户凭据、真实资源或聊天历史。

这是[Lake Security](lake-security-v1.md)后端方案之外的独立UI功能。Security的目标闭环、授权和孤儿治理维持后端改造范围；SOP清单的前端和只读API单独规划、单独PR验证。浏览SOP不是选择执行方案，也不生成任务或授权。

首期只有浏览与本地筛选：不提供新增、编辑、删除、导入、导出、市场、用户上传、模型自动学习、启用/禁用或发布；也不提供“运行”“应用到任务”“申请授权”等按钮。后端不开放对应写入/执行接口，避免仅隐藏按钮但实际可以调用。

## 2. 入口与交互

使用现有工作区菜单增加“SOP”独立条目，与“定时任务”“设置”等同层，图标复用Glyph的book。点击打开专用SOP浏览面板，不进入权限设置、聊天记录或隐藏的工作流功能。

现有 `App.tsx` 的Workflows入口由 `showWorkflows=false` 控制，不能为了显示SOP而打开该开关或复用其创建/执行逻辑。新增独立的打开状态及组件即可。浏览不要求模型已配置，也不要求选择目标资源；内置目录全应用一致，切换项目不修改清单内容。

面板布局：

```text
SOP                                                  关闭
搜索 SOP                  分类：全部 / 主机 / 服务 / 数据库 / K8s / 数据 / 通用

内置流程列表              选中的 SOP 详情
  主机资源异常排查          名称、版本、内置来源、流程影响
  服务不可用与端口排查      用途与适用条件
  数据库连接与健康检查      前置条件
  Kubernetes应用异常排查    步骤与依赖
  数据同步与一致性校验      停止与失败处理
  服务重启与恢复验证        验收条件
  通用任务处理（兜底）
```

- 列表显示名称、一句摘要、分类、版本及“内置”标识；流程含写操作时显示“包含数据变更”，不能因清单只读就把流程影响标成只读。
- 搜索只匹配名称、摘要与分类，筛选只影响显示，不改变目录或后端状态。
- 首次打开默认不自动选执行目标；可选择第一条详情用于浏览，不具有执行含义。
- 详情默认展开用途、适用条件和主要步骤；长内容使用现有DisclosureSummary折叠技术说明，避免塞满命令和参数。
- 面板关闭后保留聊天草稿、资源选择和正在运行的任务，焦点回到仍可见的工作区入口；菜单保持打开时才回到SOP条目；打开/关闭/浏览不开始、暂停或取消任务。
- 窄窗口改成列表→详情的单列浏览，提供返回列表；分类用AppSelect，图标用Glyph，使用共享主题和曲线。支持Escape关闭、键盘选择、焦点恢复、浅深色和长列表滚动。

本期不增加SOP编辑器、版本对比页、授权表单或执行控制面板。

## 3. 首批内置条目

| sopID / version | 名称 | 用途 | 流程影响 |
| --- | --- | --- | --- |
| `host-resource-diagnostics` / `1.0.0` | 主机资源异常排查 | CPU/内存/Swap/磁盘/进程与趋势取证，区分瞬时和持续异常 | 读取检查，不自动清理或停止进程 |
| `service-diagnostics` / `1.0.0` | 服务不可用与端口排查 | 进程/监听/健康状态/日志/网络及依赖，定位已排查范围 | 读取检查；建议不自动执行 |
| `database-health-check` / `1.0.0` | 数据库连接与健康检查 | 区分连接/认证/实例/连接池，检查连接数、锁等待、错误日志 | 读取检查，不修改数据/参数或终止连接 |
| `kubernetes-app-diagnostics` / `1.0.0` | Kubernetes应用异常排查 | Pod/事件/日志/探针/Service及Endpoints/发布状态 | 读取检查，不自动重启、扩缩容或发布 |
| `data-sync-verification` / `1.0.0` | 数据同步与一致性校验 | 固定源快照/目标基线→冲突规则→同步→逐项比较→闭环 | 包含数据变更；未来执行仍须另行授权 |
| `service-restart-verification` / `1.0.0` | 服务重启与恢复验证 | 基线/影响与依赖检查→授权重启→健康及业务复核 | 包含服务变更；退出成功不等于恢复成功 |
| `general-task-fallback` / `1.0.0` | 通用任务处理 | 无匹配专用SOP时，澄清→取证→方案→授权→尝试→验收/暂停 | 按本次计划决定；不自动获得任意命令权限 |

清单先显示6条专用流程，再显示唯一的通用兜底；分类/搜索不改变这个角色。服务重启详情必须说明失败后先核实服务状态，再选择已授权的恢复/补偿方式，不承诺“重启失败可自动回滚”。其余诊断类的验收是取证覆盖和结论可追溯，不承诺没有证据也能找到根因。

内置内容使用资源A/B、服务名等参数名，不写实际IP、密码、数据库地址或某次真实任务的成功结论。每个条目都说明参数是流程所需信息，本期详情不提供可提交执行的参数表单。

服务诊断的前置条件包括目标明确、时间范围和读取权限；步骤采集健康状态、日志、指标并区分事实与假设。停止条件包括目标身份变化、日志可能含秘密、需要未授权变更。输出是证据与处置建议，验收是检查覆盖及结论可追溯，不能把“已给建议”说成“服务已恢复”。

数据同步的前置条件包括固定源快照/目标基线、集合与冲突规则、备份或补偿可行性；步骤明确ID/字段保留、不覆盖条件和独立校验。结果不明先核查部分写入，不直接重跑。验收比较指定ID集合、内容及原记录保护，不只看条数或脚本退出码。没有安全补偿方法时明确“需人工处置”，不能承诺所有同步都可回滚。

### 3.1 通用兜底SOP

通用条目使用同一内容schema，标记 `kind=fallback`。它规范未知任务的推进过程，不预先提供无限命令清单：

1. **澄清目标**：确定交付结果、已知资源、限制和可核验的完成条件；目标不明确先询问。
2. **最小取证**：只在已授权范围收集必要事实，区分已知、推测与缺口；不能顺带扫描其他资源。
3. **形成方案**：把任务实例化为WorkGoal/依赖步骤，列每步操作范围、预期证据、风险、停止条件和失败处理；变更前明确验收方法。
4. **确认授权**：沿用任务一次授权机制；范围内自动执行，范围外再确认；模型生成的计划不构成权限。
5. **分步尝试**：每次执行关联原目标/步骤/attempt，失败先核实副作用再重试/替代，不能丢弃未决操作或孤儿执行。
6. **证据验收**：达到当前契约才结清；证据不足、未知副作用、资源失联或无法形成安全下一步时暂停并说明缺口，必要时人工接管。

未来执行层的选择规则：优先检查专用SOP适用性；无适用专用条目时选择本通用条目，信息不足时先走其澄清阶段；多个专用条目同样适用则请求选择。必须记录未匹配原因和所用SOP版本。目录损坏/版本不可验证、权限拒绝或原操作unknown不是“没有匹配SOP”，必须按原错误/限制处理，不能切通用流程绕过。

本期只把通用条目和这套规则展示在手册中，不实现自动匹配接口或执行入口。未来接入时“走通用SOP”只决定步骤组织方式，不放宽Security边界，也不保证所有未知任务都能自动完成。

## 4. 内容模型与只读API

新增 `internal/sop` 作为应用内独立只读内容包，与ADK、模型和工具执行器解耦。`builtin/*.json`由go:embed随签名应用打包；应用升级可以更新内置条目，本期不在线下载或把目录写入用户数据库。

固定模型：`id/version/source=builtin/kind=standard|fallback/title/summary/category/impact/applicability/parameters/preconditions/steps/stopConditions/failureHandling/acceptanceCriteria`。step包含稳定id、title、description、dependsOn、expectedEvidence；parameters只描述名称/类型/用途，不保存值。可选rollback说明放failureHandling中，必须区分取消、补偿和不可逆影响。

内容字段进一步固定为：step的expectedEvidence包含稳定证据键和说明；stopConditions/failureHandling各条都有稳定id及触发/处理说明；acceptanceCriteria各条含id、description、completionLevel（diagnostic/delivery/recovery，通用模板可用goal_contract并须在实例化前按原目标解析）、requiredEvidence（模板证据键）、required和预定义适用条件。ID和依赖对应详细规范，检查引用不可悬空；验收结果输出不能反过来作为自己的通过证据。静态schema校验仅验证内容完整性，首期不执行条件表达式、验证器或命令。

包加载时验证ID/版本唯一、source固定builtin、7条内容中恰好1条kind=fallback且ID为general-task-fallback、步骤ID唯一且依赖存在/无环、前置/停止/验收内容非空。以排序后的内容hash生成catalogVersion；坏条目使目录加载返回明确错误，不发布半份内容。

逐项内容验收还包括：四个诊断SOP不能把diagnostic_complete展示为问题修复；同步必须保留快照/部分写入/原记录保护条件；重启必须有业务稳定窗口验证；通用流程必须允许安全暂停且不能绕过权限/unknown。JSON完成条件保留上述区别，详情浏览不得只显示步骤名称而省略停止/失败/验收说明。

| 拟新增接口 | 行为 |
| --- | --- |
| `GET /api/sops` | 返回catalogVersion及内置摘要列表，顺序稳定；不触发项目/资源/模型查询 |
| `GET /api/sops/:id?version=...` | 返回匹配版本的完整详情；未知ID返回404，版本变化返回明确刷新提示 |

沿用 `Server.authorized/protect` 的本地认证与来源检查。只返回注册的内置字段；不接受文件路径，不加载远程URL，不包含Shell运行端点。不支持POST/PUT/PATCH/DELETE和执行子路径；明确返回405或404，不转发到workflow、SRE工具或命令bridge。

前端增加独立SopSummary/SopDetail类型与api读取方法是本SOP功能的改动，不作为Security控制面协议的扩张。加载/错误/重试/筛选为空均使用普通已有界面模式，禁止静默将失败当“没有SOP”。文本按普通React文本/受限Markdown展示，不启用原始HTML或脚本。

## 5. 与任务闭环的边界

```mermaid
flowchart LR
    B[随应用发布的内置SOP] --> R[只读内容注册表]
    R --> API[GET 列表 / GET 详情]
    API --> UI[SOP清单与详情]
    R -.未来独立阶段：验证适用条件并实例化.-> P[WorkGoal / 步骤计划]
    P -.仍需正常安全判定.-> S[任务授权 / 派发 / 证据 / 验收]
```

虚线部分不属于首期。浏览版本号或“内置”标识不代表任何任务已获授权；即使后续引入“应用SOP”，也必须由后端按可信sopID/version/contentHash取得模板，不信任前端传回的步骤或模型生成的同名文档。SOP只是步骤与验收模板，不能成为跳过Security的凭证。

## 6. 实施位置与验收

拟新增：`internal/sop/catalog.go`、`builtin/*.json`、`internal/web/sop_routes.go`、`web-agent/web/src/SopCatalog.tsx`和独立样式/前端测试。现有 `server.go`注册只读路由；`SidebarUtilities.tsx/App.tsx`接入口和打开状态；shared/contracts.ts/api.ts只增加目录读取类型/方法。具体任务见[独立计划](../../plan/feature-builtin-sop-catalog-1.md)。

验收要求：7个条目内容完整、通用兜底唯一且流程影响表述准确、列表详情版本一致、搜索/分类正确、无项目/无模型也能浏览、加载错误可恢复、窄窗和键盘可用；打开/切换/关闭SOP时调用记录仅有目录GET，不创建goal/workflow、调用模型、申请权限或执行命令。检查无写接口、无自动匹配/执行入口、无真实资源数据泄漏。未来功能实施需在独立PR运行相应Go/前端检查与Lake Dev验证；本次只是设计文档。
