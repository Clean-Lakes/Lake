# P7 在线只读纠错 v1

P7 在正常任务的官方 ADK 调度中增加受限的修订工具和执行门禁。它不新增模型/工具循环，不引入 Python、独立 Agent 服务或自动写操作，也不自动保存、采用或升级用户策略资产。P6 的隔离快照优化继续独立存在。

## 开关与生效范围

兼容新增 `onlineCorrectEnabled`，缺失时为 false；旧数据库和旧客户端的 `correctEnabled=true` 只保留原来的隔离实验授权。在线行为必须同时满足 `masterEnabled && correctEnabled && onlineCorrectEnabled`。全局与已保存项目设置逐项取交集，预算取较小值。`applyEnabled`、`learnEnabled` 独立控制资产应用与学习候选，不是在线执行授权。

设置仍保存在已有 v4 Web 仓库的 JSON body 中，无需改写或迁移旧 DDL/hash。关闭开关、撤销来源导致 epoch 变化后，每次模型请求、提案和工具调用均通过可信宿主重新检查；SRE 子角色也检查父会话的真实项目。当前执行中的外部效果依然保留在操作账本，关闭开关不宣称撤销效果。

支持普通 Web/Desktop core、terminal2、数据库元数据检查，以及现有 SRE 专家工具执行链。CLI/stdio 不自行配置这些宿主标志。工作流和 SRE 对话协调器没有修订工具；SRE 专家的请求、额度及记录归同一个父任务，计划/角色变更不清零。无工具角色不因 P7 获得资源执行能力。

## 分类与执行

1. 正常工具先经过原有 catalog/schema、目标范围、policy、权限及操作账本。只有真实错误/失败才建立在线记录，正常回复不额外显示提示卡。
2. 可信只读白名单包括文件读取/搜索、数据库元数据、Docker 列表/日志、固定 observe_* 探针。Shell/终端还必须获得当前宿主 policy 的只读证明；不透明 SQL、MCP、未知工具、写入、传输、后台操作均不作为纠错检查。
3. 模型通过 `revise_readonly_strategy` 提交七个字段：真实失败调用 ID、被否定假设、实际修改、预期信息、停止条件、一个工具名、一个 JSON 参数对象字符串。拒绝重复 JSON 键、未知/额外字段、超限内容、敏感内容、伪造来源和递归修订。
4. 提案只登记下一项检查，不能授予权限。下一调用必须完全匹配提案，重新通过正常校验和可信 policy，保持已确认资源/运行时/容器/数据库范围；HTTP 健康检查 URL 也冻结。目标变化、缺失授权或需要新增确认时停止，不换角色、终端或入口绕过。
5. 原操作仍 dispatched 或父任务有其他在途调用时不采样。未知只读操作返回后可新建独立调用，旧 unknown 身份与结果不改写；未知修改/不透明操作交回现有 reconcile。

瞬时只读错误或已返回的只读 unknown 才能对同一逻辑检查进行额外采样。网络异常来自执行器错误或受信只读 curl 健康检查的结构化传输退出码 6/7/28/52/56，不根据 stderr 中的自然语言或模型声称认定成功。curl HTTP 错误、证书/认证错误不降为瞬时错误。命令带显式 retry 时不叠加纠错；现有固定探针自身的更严格次数限制仍生效。没有为工具再增加隐式网络重试。

curl 退出码依据：[curl 官方错误码](https://curl.se/libcurl/c/libcurl-errors.html)。实际可执行命令仍以 Lake 既有只读分类器为准；v1 的 curl 只接受本机固定健康端点的 GET/HEAD。

## 进展、预算和停止

保存原失败和所有后续失败检查的缺口集合，而不是只记最后一条失败。检查身份由工具及规范参数 hash 决定（仅排除超时等采样控制参数），目标另行冻结。只有同一可信检查在同一目标取得实际成功结果才能关闭对应缺口；另一文件/日志读取成功、换措辞、新调用 ID、新时间戳或缓存重放均不足以证明原缺口关闭。关闭另一项失败也不会丢掉原始未解决缺口。

每任务最多 2 次修订、同检查最多 2 次额外采样、连续 2 次未确认进展即停止。P7 另外将观察总数限制在 `maxRuns`（默认 6）内。源失败前的正常模型请求不算“附加请求”；从失败开始的提案、执行调度、最终报告、输出恢复以及其他 SRE 角色请求统一计入最多 12 次附加模型请求、100000 token、600 秒活动时间，且继续受原任务更严格的步数/用量限制。

每次 provider 派发前持久化请求与 token 预留；已知 usage 结算，未知保留预留且累计未知标记，不被后续已知 usage 覆盖。到达任一额度停止，不另设辅助 compaction 请求。宿主在同一时刻只接纳一项在线纠错；角色请求/工具在父任务串行认领。所有调用继续复用现有模型/子任务限流。

兼容最新 develop 的实时进度综合：当前轮出现在线纠错记录后，不再从 UI 另起额度外的模型进度摘要；原资源记录、阶段事实和纠错任务卡仍可查看。旧轮已完成的记录不影响新轮普通进度摘要。纠错阶段请求计数包含该阶段的最终报告，是保守预算计量，不等于相对未开启场景的净增请求数。

停止原因使用现有枚举。模型结束回复不能关闭运行时缺口；仍有失败检查时角色/任务结束为等待继续或失败，不能因一段“已恢复”的文字转为成功。权限拒绝、目标不明、能力不可用、预算、无进展和外部结果待核实均明确保留。

## 持久化、恢复和继续

官方运行时数据库 `sessions.sqlite` 增加独立的 `native_corrections` 表，存储有版本的报告 JSON；主键是父会话加本轮 ID，SRE 则是父会话加任务 ID。记录在派发前提交，ADK UI projection/本地缓存不具有退回计数的权力。快照从该表修复任务卡，缓存丢失或旧 projection 不清除账本。此为现有 native GORM 初始化中的增量新表，Web v1～v4 的冻结 schema 和兼容备份流程不变。

启动只把未结束记录置为等待：在途调用/请求为 awaiting_reconciliation，已保存已知状态为 awaiting_user；不自动执行。未知请求/工具保持身份和保守计费，不通过重启重试。崩溃时未结算活动时间按剩余上限保守计入。

现有 SRE 显式 start/continue 路径仅能恢复 awaiting_user、具有可信只读缺口、无在途身份且预算仍剩余的记录；重验原模型、权限 hash、全局/项目 epoch。等待停止活动计时，单次等待 24 小时有效；恢复不退款或重建记录。到期、配置变化、权限阻断、未知派发或预算耗尽时保留历史，要求新任务或现有核实流程。修改计划/切换角色不是新预算。

清空模型上下文不会清除纠错和外部操作账本。报告只保留真实调用 ID、证据/检查/目标 hash、提案解释、实际 manifest 引用、实际采用的资产版本、模型引用、设置 epoch 和计数，不复制原始工具输出、完整提示词、密钥或模型 URL；原始证据继续按原工具审计规则保存。

## 可见性与比较限制

新增任务卡显示停止原因、修订/进展/无进展、附加请求、保守 token、真实调用/证据 hash、提案和版本信息；浅/深色及窄窗口使用现有组件和主题曲线。原检查取得结果不等于业务整体恢复，仍以 SRE 原有验收契约为准。

普通任务的 before/after 可以通过独立开关和现有会话快照读取、按任务/模型/epoch/实际资产版本比较观察。它们不是配对因果实验，没有伪造“提升百分比”或把不同任务合计成成功率。P5/P6 固定快照评估继续提供隔离 A/B 和阶段 A/B/C；真实模型的代表任务、三次以上配对样本和推广门槛留在 P8。
