# 任务计划与结果报告

## 当前 TypeScript 合同（2026-11-12）

用户明确要求取消后台待核实和验收机制。Agent 通过 `work_finish(summary, outcome)` 提交报告；completed 与 partial 均结束本次执行，partial 保留未完成部分和限制。报告结束执行，不提供独立业务成功证明。宿主不再要求成功工具集合、全部步骤验收或原 unknown 结清，不再写新的 `superAcceptance`。多人任务在成员提交后汇总报告，不生成共同验收或“已核验”公告。

新调用不受旧任务、项目、共同成员或 MCP 服务的 unknown/dispatched、旧 Go 未决记录及参数去重锁阻断。原 call ID 仍幂等，不重复执行；不确定结果继续作为原操作事实保存。核实/影响复核 API 退役为 HTTP 410，页面移除核实表单。停止正常关闭执行，不因未知回执改成 blocked；实际后台命令与 child 的汇合、取消和清理仍保留。

当前资源归属、明确范围/deny、凭据及连接版本、Pilot 操作审批、Plan 只读与计划确认、Worker lease/generation、权限版本和原截止时间仍逐次校验。配置修改的 pending/unknown 提交回执属于配置事务，继续防止盲目重复保存，不是本次移除的业务验收。Home 安全身份和 Memory 同意/来源约束保持。

已有操作、已结算尝试、验收和报告不批量改写；兼容字段不代表新验收决定。后续重新检查使用真实新输入和当前权限，保留上一份报告。上下文引用已撤回知识时，普通已结束报告也可建立同专员独立只读复查，仍限原明确资源与原期限，不继承旧知识或重放原调用。Memory 只采集真实来源及 hash 匹配的已结算观测，新报告标为 reported，不标为 accepted；unknown 不形成成功来源。

下方是早期实现、旧 Go 与历史合同说明，其中 TS 验收和待核实拦截由本节替代。见[当前计划](../../plan/refactor-task-result-lifecycle-1.md)。

2026-11-11 按用户最新明确要求，TypeScript SSH 首次及已存公钥变化均在后台沿原校验路径保存观察到的公钥，再继续认证，不弹指纹确认。已有算法作为偏好而非排他限制，支持正常密钥算法轮换；保存失败、配置变化或取消不能继续认证。新公钥不使旧身份回执重新有效，不替代 Pilot 操作权限、任务资格或业务验收，不重放旧任务。见[当前计划](../../plan/refactor-ssh-trust-specialist-view-1.md)。

2026-11-09 当前 TypeScript 操作审批由项目 Pilot 的执行偏好统一决定。相应开关开启后，不再因命令风险分类、解释器、SDK build 默认策略、MCP 传输类型或旧策略的单次 ask 额外弹确认；关闭后在真实操作前逐次请求确认。原风险/只读证据仍照实保存，明确 deny、受限模板、无效旧策略、专用任务授权缺失、连接/凭据版本、SSH 信任、Plan/用户明确只读、停止与任务资格继续检查。计划确认、人的终端控制权交接以及业务缺失信息不属于操作偏好审批，不自动代答。旧待确认提案不转为已批准、不回放原调用。

使用现有问答卡片和原生审批，不增加 UI 或共享 DTO。提案、人工要求确认、资源权限和结果验收分别关联到同一目标，互不替代。

## Super-agent 普通任务与 Plan 模式

专员普通任务在 `work_begin` 注册完整步骤后自动激活原任务，不弹计划确认或逐项人工验收问题。契约、SecurityTask、原根绑定与 owner 在同一派发屏障事务中建立，绑定实际来源、项目、冻结计划及原绝对期限；这不签发资源 grant，也不延长任务期限。Plan 模式仍通过真实问答卡片确认计划，确认后采用相同的工具结果验收；Plan 的只读限制仍生效，MCP 执行及变更需使用既有模式切换/执行计划入口。

`tool_results` 契约由宿主核对原步骤/尝试中全部已成功结算操作的真实 completed 回执。操作描述摘要、任务与版本、调用身份、连接、凭据、项目策略及 MCP 配置/绑定仍须匹配。MCP 发现可以验证自己刚提交的目录修订，但回执中的目录摘要必须与当前目录完全一致，其他权限检查保持有效。失败、未知、缺失、错误或错属的回执不能通过；有效的零数量或空查询结果可以通过。汇总时重新校验原回执，历史 pass 不是永久成功位。

此模式证明实际工具结果已取得，由 Worker 结合用户要求决定是否交付；它不冒充独立业务断言或人工核实。已冻结的 manual 契约与显式业务条件不改写，旧待确认卡片也不伪造用户答复。非专员受管理会话沿用下述人工流程。资源操作继续经过当前策略与原生审批，Memory 同意不受影响。

## 人工任务要求

受管理会话的 `work_begin` 先保存提案。新提案没有 SecurityTask、grant 或资源执行权限。后端将完整目标、原始请求、资源绑定、步骤和依赖冻结为私有 proposal，并通过原有官方 SDK input checkpoint 提问。

确认只建立逐步骤的 manual/human_verified 验收契约，再为这个首次提案建立 SecurityTask、根绑定与 owner。它保留原 root、真实源消息和目标最初的 DeadlineAt；已有任务不会通过此确认续期。后续实际 I/O 仍须通过当前策略、scope、预算和原生审批。拒绝、过期、步骤变化或原 root 已结束时不激活执行任务。

这类问题使用独立的 host 生成 QuestionID，不复用普通模型问题的 QuestionDecisions 缓存。同一会话/root 同时只保留一个未过期的 host 确认。答复记录绑定原问题摘要、源、版本和实际答案；模型生成的“已确认”文字不产生这条记录。完整提案无法在既有问题长度限制内展示时拒绝，不截断隐藏条件。

## 关闭失效问题

确认卡片的有效性绑定原 store/epoch、项目、任务、来源、root 和期限。后端读取闲置会话时，将过期、已换轮次、任务已终结或已结束交互的残留问题移出当前等待状态；pending 问题登记为 expired，原问题及已有答案历史保留。有效的 SDK 待输入仍能跨正常重启恢复。

跳过失效卡片只关闭等待，不记录答案、不恢复旧 SDK checkpoint、不建立契约、授权或人工验收；重复关闭可以安全重入。过期的肯定答复仍被拒绝并清除失效卡片。停止会取消当前执行并关闭残留问题，完成任务的结果与验收保持原样；未完成任务仍按原取消流程处理，未决操作不因此消失。旧问题取消回调不能清除新轮次的问题。

## 人工结果验收

执行成功与业务验收分别保存。自动适配器无法证明 manual 契约时，先保留不足的自动验收结果；只有原 canonical attempt 与全部操作已成功结算，才可再问一次独立人工核实问题。用户看到当前步骤的全部条件，并可选择全部满足或保留未完成。

人工 pass 在同一任务写事务中重新核对当前 goal/plan/step/progress 版本、attempt、条件摘要、原始操作快照，以及 answered 的真实 manual_work_verification 问题。条件、原结果或未决副作用变化都会拒绝；人工 yes 不解除 unknown、不覆盖失败或取消记录。

`workAcceptanceRecord.SourceKind=question`、`SourceInteractionID=QuestionID` 显式证明真实问题交互。`SourceMessageID` 仅保留原始来源关联，不能把原任务请求冒充验收声明；不伪造新的用户消息。验收记录和问题的 manual_verified 状态原子提交，同一动作可重入。目标汇总再次核对该独立来源，历史 pass 不成为永久成功位。

原有已鉴权管理验收 API 保持不变，记录 `SourceKind=user_action`；实际用户消息 ID 只保留为请求来源，不把原请求当成人工验收声明。普通问答、确认任务要求和模型总结均不能调用人工 pass 的可信分支。

## TypeScript 命令执行：历史待核实状态不再作为门禁

2026-11-09 用户要求移除命令的待核实阻断机制。新 Bash 调用依据当前资源、策略、审批偏好、Worker 代次和任务状态派发，不再查询原任务/项目/旧 Go/共同成员/SSH 别名的历史 unknown 或已核实变更目录来拒绝执行；命令相同但调用 ID 不同也不被历史参数去重拦住。显式计划可以创建新的尝试，保留原未知尝试，不自动核实。通配符、重定向或未识别语法仍按原风险分类选择确认方式，但不再触发另一层“先处理旧操作”的锁。

原调用 ID 不重新执行，重启不自动重放；当前执行仍检查资源归属、准确配置、SSH 指纹、权限、停止和期限。原失败和 unknown 保留，验收不能把它们算作成功。Plan、明确只读范围和非命令适配器的合同不随该改动放开。下面早期恢复说明中关于冲突变更阻断、变更目录围栏及已接收请求二次围栏的规则，不再适用于新的 TypeScript Bash 调用。

## 权限与恢复（早期实现及非命令合同）

TypeScript SSH 命令记录持久化 `not_sent → exec_requested → channel_open` 阶段，在调用传输层 exec **之前**先写入 `exec_requested`。只在宿主记录与原 Task/Worker/Session、generation、调用 ID、资源和配置版本全部匹配，且终态明确保留 `not_sent` 时，才把失败记为无已派发命令的失败；可在原权限内创建新的尝试/调用，不能重放原调用 ID，也不把失败当业务成功。显式计划沿原步骤及契约重试。请求过 exec 后的断线、缺失阶段的旧记录及来源不完整的结果继续保留未知，不以 stderr 的文字判断未执行。

字面量 `date -Is` 等 ISO 显示、`last` 重启记录和 `journalctl --no-pager` 的受支持查询选项按只读处理；设置时间、journal 维护、分页、动态执行、输出文件重定向及未知参数不因此获得只读证明。当前资源/策略检查仍逐次执行。原未知操作不阻断另外允许的只读查询，但仍阻断冲突变更和目标验收，不自动改写历史状态。原普通任务未完成或含未决操作，也可以通过 followup（记忆失效时）或 create + predecessor_task_id 建立同一专员的独立只读复查；不以原任务成功验收作为新观测的前提。两个入口沿同一宿主方法保留原明确资源、原截止时间与旧账本；新复查不导入旧上下文或结清旧 unknown。显式计划、共同任务、期限及当前权限保持原门禁。

原目标受阻后，实际当前执行上下文可以为原步骤激活一次重试，不要求模型先把整个目标伪装成 running。依赖、契约版本、当前 task/root、Super-agent assignment 和未决操作检查仍在同一派发屏障内生效。原 prepared 尝试只有在规范操作账本计数为零、契约一致且原 task 仍属于当前 store/epoch 时，才可记录为 not_executed/reconciled，并追加宿主审计后创建带 retryOf 的新尝试；这不产生业务验收。存在原操作时不能走空尝试路径；unknown 或不明派发状态仍须按原核实协议处理，不能借步骤重试清除风险、跨恢复纪元继承旧执行资格或重放操作。

同一目标后续真实轮次可以继续取得新的只读观测：原尝试的所有操作必须已成功结束、具有可校验的非 opaque 只读 descriptor，且原资源连接、契约和 store/epoch 仍匹配。宿主只把该尝试的执行事实记为 succeeded/reconciled 并追加审计，为当前有效 task/root 建立带 retryOf 的新尝试；不复用旧 permit、不重放原操作、不生成业务 pass。原成功写入、未知结果、未结束操作及描述不完整的历史均不能借此刷新；权限、调用额度和绝对期限继续按当前状态检查。

效果判定使用经过校验的冻结 descriptor。通用 Shell 的旧 risk 字段可能仍是 write，但已登记、冻结并成功返回的 disk_usage/process_snapshot 等只读诊断不因此冒充未核实写入；原 risk、status、result 和 descriptor 均保持原样。opaque Shell 或真正包含写入能力的操作不能借此继续。

once/task 的问答只记录授权提案。最终原生审批必须展示并绑定实际资源、能力、profile、task revision、绝对到期时间、预算和 envelope 差异；签约仍在原审批领取事务中完成。签约后使用新 descriptor，旧单次批准不能扩成批量授权。

恢复保全原问题和验收历史，使未完成提案失效并切换 epoch；不从旧问答自动创建新权限，也不复用旧 owner。Memory 的同意与遗忘资格另行核验，任务或人工验收不表示 Memory 同意。
