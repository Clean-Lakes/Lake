## 保留的失败与限制

场景 3 原始回答写了「200 次请求、7 次失败、193 次成功」，但同时写「93% 成功」，正确成功率应为 **96.5%**。原始错误保留，没有重跑覆盖、改分或把停用后的另一份正确回答算成该样本修复。这是模型输出质量问题；本 PR 不修改模型权重、不增加自动重试，也没有声称修好了算术可靠性。

部分回答仍有「偏低」「整体可用」等缺少明确阈值支持的评判。此验收没有完整语义裁判；候选审核和注入清单不能证明所有事实、阈值判断或建议都正确。

维护来源被提取为报告指导，正文有条件且不是成功经验。试验验证了关键词筛选；没有覆盖 `domain_procedure` 的模型/工具变化停用，更没有证明自然语言前置条件能被系统自动执行。相关独立边界见 R4 原有回归。

## 修复的验收问题

同会话的第二条消息通过 `/messages` 接受后会排队，旧轮次的 `completed` 快照可能暂时仍可读取。原 `Lake.finish()` 会立刻接受旧回答。此次采集中遇到该竞争后，只重新读取了实际新轮次，未再次发送纠正消息，后台仍只有一次相应提取。

增加 `send_and_finish()`：发送前记录 `rootTurnId`，仅派发一次，等待不同且非空的新轮次终态；新轮次失败保留失败，等待超时不重发。已有“等待当前取消/中断收尾”的调用仍可用 `finish()`。两个现有 Dev 脚本的普通消息发送改用此入口。

新增 5 项无网络、无模型回归，覆盖旧 completed/缺少新身份超时、快速新轮次失败、排队后进入新终态、新审批不是成功，以及当前轮取消收尾兼容。另在实际 Dev 的已完成会话发送一条独立「已核对」消息，确认等待到了不同的新轮次 ID；这不是对场景 3 的重跑。

同时修正用户指南：R5 已完成，不再引导已退役的发起/续跑/保存优化操作；补齐明确纠正前缀、普通模式限制及当前评估入口。
