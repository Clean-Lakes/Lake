## 定位与变更

日常 Dev 的专员状态接口单次耗时 702–1461 毫秒，前端每 2.5 秒轮询，刷新事件也会触发请求。该同步计算占用 Node 事件循环，使会话加载、发送请求和其他 API 一并等待。

用当前 TS 数据库的一致副本剖析，单次 workspace 请求为 936 毫秒，其中 `messages()` 累计 924 毫秒。4 个专员的未读检查合计调用 29 次；每次 `messages(sessionId)` 都先 `list('messages')` 读取、解析所有会话正文，再用 JavaScript 筛选所属会话。历史变大后，这个路径成了重复的全量解码。Magpie 同步接口约 2 毫秒，并非这次主要瓶颈。

`LakeStore.open()` 现在建立按消息 `sessionId` 的 SQLite 部分表达式索引；`messages()` 先按准确会话查询，再解析匹配行，继续按原 `rowid` 返回。SQLite 在原有插入、编辑、改归属和删除事务中维护索引；不缓存旧正文/未读状态，不删除历史，不改变权限与任务执行语义。

## 性能验证

隔离数据副本使用相同 backend/workspace 代码，分别启用原全量扫描和新索引读取；每种状态运行 3 次。没有外部业务工具调用。第二个隔离 HTTP 场景同时请求原项目的专员状态并向新 QA Pilot 发送合成消息；本地模型网关保持响应未返回，直到 POST 已接受，避免把模型生成时间混入消息准入。

| 场景 | 原读取方式 | 索引读取 |
| --- | --- | --- |
| 相同副本 workspace 三次 | 794.1 / 779.6 / 936.9 ms | 7.2 / 7.3 / 7.2 ms |
| 同时刷新专员状态时的消息接受 | 870.8 ms | 57.6 ms |

上述发送对比每种状态只有一次，是定位用观测，不作为统计分位数。两个状态均在模型网关仍等待时返回接受结果，之后模型正常完成；不声称远端模型本身变快。

更新后的日常签名 Dev（实际既有 Home，3 次 GET）另测得：

| 接口 | 耗时 |
| --- | --- |
| bootstrap | 3.8 / 8.1 / 3.2 ms |

原生 Lake Dev 已检查 Pilot 与知识库专员的切换，历史内容可见、输入区可用。表格度量为后端 HTTP 往返，不将其当作渲染帧或远端首字延迟。
