# Lake Web Agent：产品与首版发布方案

## 1. 产品定义

**Lake 是以项目归类、以会话为工作主体的运维 Agent 客户端。** 用户在一个项目下创建会话，以自然语言交代排障目标；主 Agent 调度多职能专员调查，汇总有来源的证据，提出下一步操作。项目左侧同时列出会话和可用资源；用户在当前会话中观察、批准、接管或中断操作。终端在会话内展开，不弹出独立会话。

目标用户：需要在主机、日志、指标、容器和其他资源之间排查问题的个人值班工程师或小型运维团队。Web 首版优先验证一名使用者、一个项目、一个故障会话的完整体验；团队共享、租户管理和远程生产托管另立需求。

一句话体验：**选项目 → 打开会话 → 描述问题 → 看专员调查与终端证据 → 确认操作 → 看验证结果。**

这是一份新的产品方案。仓库里的旧 Lake Agent、插件与客户端可供验证技术细节，但其数据模型、授权逻辑和产品边界不构成本方案的约束；任何复用都要逐项评估。此文档不宣称新 Web 产品已实现。

## 2. Web 首版的用户体验

```text
┌─────────────────────────┬─────────────────────────────────────────────┐
│ 项目                     │ 当前会话：排查 web 服务 502                 │
│ ▾ 生产项目               │ 用户目标 / 主 Agent 阶段性结论              │
│   会话                   │ ┌ 主机专员：检查进程和本机日志  [查看证据] ┐ │
│   · 排查 web 服务 502    │ └ 变更专员：核对最近发布       [查看证据] ┘ │
│   · 回顾昨日发布          │ 操作提案：目标、命令、影响、验证 [批准/拒绝] │
│   资源                   │ [当前会话的终端抽屉：web-01  · 已连接]       │
│   · web-01   已连接      │ 消息输入                                    │
│   · db-01    未连接      │                                             │
│ ▸ 测试项目               │ 点击 web-01 → 当前窗口内的资源详情          │
└─────────────────────────┴─────────────────────────────────────────────┘
```

- 左侧按项目组织两类入口：**会话**是持续工作的主体，**资源**是项目下可连接的目标（主机、服务，后续可扩展容器或数据库）。资源行显示名称、类型和连接状态；未连接的资源仍可查看。资源列表可展开或收起，但不替换会话导航。
- 点会话打开主工作区；点资源在**同一窗口**打开资源详情，显示地址或标识、环境、状态、已关联的会话和可用终端。资源详情可选择“在当前会话中使用”或“新建会话使用”，避免不知命令属于哪个会话。没有当前会话时，手动连接资源先创建或选择会话。
- 终端归属具体会话和资源。当前会话里的终端从资源详情、对话中的命令步骤或终端抽屉进入；抽屉以标签区分目标和连接状态。打开资源详情后返回会话，终端与 Agent 的调查过程仍继续。对历史会话而言，资源目录不等于终端历史，历史命令和输出在所属会话中查看。
- Web 主界面采用 Claude 客户端式的会话阅读方式：左侧是安静的项目/会话/资源导航，中间是限宽的连续对话，底部始终可见输入框；新会话先引导用户描述问题，不以仪表盘或密集卡片作为首页。Lake 保留自己的名称、色彩和图形，不复制 Claude 的品牌标识。
- 主对话按时间展示用户指令、主 Agent 的计划与结论；专员活动和证据以可展开的内嵌工作步骤呈现，审批在相应消息旁清晰列出目标、完整命令、影响和验证方式。只有展开时才显示完整命令输出和专员详细过程，保持聊天阅读的连贯性。
- 一个主会话可关联多个资源和终端；每条操作都显示精确目标、会话与发起者。用户输入与 Agent 输入共用同一可见工作现场，不弹独立窗口。
- 刷新或离开页面后，会话和专员状态从服务端恢复。若真实终端已断开，界面明确显示“断开”，历史输出不能冒充仍然存活的 shell。

## 3. Agent 的职能与边界

### 主 Agent（协调者）

接收目标，读取当前会话和项目作用域，拆分调查任务，选择专员并跟踪进度。它比较专员发现、标记证据之间的冲突或过期数据；证据不足则继续调查，不能把猜测写成既定根因。它给用户一个可复核的结论，以及具体的下一步操作或需要用户补充的问题。

### 职能专员（按需启动的子 Agent）

首批能力按工作划分，而非按某个连接协议命名：

- **主机与终端专员**：服务状态、进程、文件与终端输出的调查。
- **日志与指标专员**：故障时间窗、异常和业务影响的调查。
- **变更专员**：最近发布、配置变化与故障发生时间的关联分析。

Kubernetes、数据库、容器等可先作为受限工具能力，等具体场景证明需要独立上下文和调查方法时再新增专员。专员持有自己的任务、模型上下文、工具范围和成本预算；产出结构化发现（结论、证据 ID、来源、采集时间、不确定性、建议检查），回到同一主会话。并行调查允许各专员使用独立连接；**同一个交互终端的输入只有一个持有者**，用户接管优先，其他输入排队或被拒绝。

### 终端与执行

浏览器在当前会话的终端抽屉中显示终端；项目资源详情提供查看或关联终端的入口。服务端持有 PTY/SSH 会话、连接状态和授权；每个终端明确绑定项目、资源和会话，不能仅通过点击资源把命令发到另一个会话。Agent 可以读取其获准查看的输出与结构化命令结果。读命令与变更命令均须经过目标解析与权限检查：首版可对已定义、受限的诊断动作授予会话内只读权限；任意自由形式的终端输入和所有生产变更在发送前展示目标、命令、预期影响并要求人确认。审批绑定本次操作，不能因为终端已连接就自动扩大权限。

用户在终端手动输入期间，Agent 不抢占同一终端。长期运行命令支持实时输出、显式中断与结果状态；断线后不重发可能已经执行的命令，先核查实际结果。命令退出码只是执行事实，不能单独证明故障已恢复。

## 4. 从 Google SRE 文章借鉴的能力等级

参考 [AI in SRE: How Google is Engineering the Future of Reliable Operations](https://sre.google/resources/practices-and-processes/ai-engineering-reliable-operations/)，自主权按**操作和场景**授予，不按“这个 Agent 值得信任”整体授予：

| 等级 | Lake 中的行为 | Web 首版 |
|---|---|---|
| L1 | Agent 调查、归纳证据和提出检查/处置建议；人决定并操作 | 首要目标；常规诊断按明确授权执行 |
| L2 | Agent 提出具体操作；人批准后由独立执行层执行并复测 | 仅在受限、可验收的场景试点 |
| L3 | 限定场景、限定目标内无需事前批准地执行 | 不进入首版 |
| L4 | 跨步骤自适应完成故障处置 | 不进入首版 |

Google 文中的 AI Operator 可并行调查并启动专业子 Agent；其 Actuation Agent 另行检查处置提案、dry run、生产风险和审批。Lake 据此将**推理/提案**与**操作控制/执行**分离。执行层负责冻结目标与参数、检查权限和当前状态、处理审批与冲突、记录结果、进行独立健康验证并支持中断；模型输出与远端终端文本都不能直接授予权限。首版可以只提供有限的变更类型，优先完成可信的 L1 调查闭环。

## 5. 技术选型（开源、Web 优先）

- **前端**：[Vite + React + TypeScript](https://github.com/vitejs/vite) 构建 Web 工作台；[assistant-ui](https://github.com/assistant-ui/assistant-ui)（MIT）提供对话、工具调用和审批组件；项目侧栏、专员进度、证据视图由 Lake 实现。用 [shadcn/ui](https://github.com/shadcn-ui/ui)（MIT）搭建界面，用 [xterm.js](https://github.com/xtermjs/xterm.js)（MIT）显示内嵌终端。
- **Agent 服务**：Node.js + TypeScript；主 Agent、专员、终端服务、操作控制层和持久化服务拥有明确接口。服务端是会话事实来源，网页关闭不终止服务端任务。Web UI 与 Agent 服务同源部署，之后的桌面客户端使用同一会话 API。
- **实时传输**：对话、专员和操作事件使用带序号的流与服务端快照，页面断线后按游标补齐并去重；终端输入输出采用双向通道，另实现背压和会话重连。快照、事件、终端输出分别管理，避免以无限增长的聊天文本代替状态和日志。
- **协议候选**：[AG-UI](https://github.com/ag-ui-protocol/ag-ui)（MIT）的消息、工具、[子 Agent 事件](https://docs.ag-ui.com/concepts/subagents)和[审批中断](https://docs.ag-ui.com/concepts/interrupts)值得评估；它不负责 Lake 的项目权限、会话持久化、PTY 生命周期和断线重放。先用一个纵向原型验证与 assistant-ui 的适配成本，再冻结 Web 事件协议。
- **完整产品参考**：[OpenHands Canvas](https://github.com/OpenHands/OpenHands)（MIT）可参考会话/终端工作台；其组件和 Agent Server 契约绑定较深，不预设为 Lake 的运行时或整站基础。[LibreChat](https://github.com/LibreChat-AI/LibreChat) 可参考项目归类对话，但终端协作仍需单独实现。

首版存储需支持项目、会话、专员任务、权限、操作与审批、证据、事件及终端元数据。采用私有数据库和凭据存储；API key、SSH 私钥及原始敏感输出不进入普通模型消息与前端事件。浏览器访问、会话授权及终端输入须按服务端身份校验。首版可以采用单实例部署，但应在发布材料中明确运行环境及备份/恢复方式。

## 6. 可验收的首个纵向场景

一个项目中，用户创建“排查 web 服务 502”会话，从左侧资源列表选择获授权的测试主机及服务，并在当前会话中关联终端：

1. 用户从资源详情进入当前会话的终端抽屉，运行诊断命令，或粘贴并选中报错；主 Agent 从当前会话读取命令、退出状态和对应输出。
2. 主 Agent 并行派出主机和日志/变更专员；前端实时显示专员状态、目标和工具步骤，全部返回同一个主会话。
3. 主 Agent 引用具体输出和时间提出一个可验证的假设，并指出不确定之处；用户可展开来源。
4. Agent 提议下一步操作，界面展示资源身份、准确命令、可能影响和验证方式。审批只授权本次明确操作；用户可拒绝、中断或接管终端。
5. 执行后重新采集业务健康与相关证据。如果操作失败或结果不明，界面保留状态，Agent 不重复派发已执行的命令。
6. 刷新浏览器后，项目、会话、专员结果、审批与证据恢复；已断开的真实终端显示断开。

测试目标必须与生产资源隔离。首版不以“Agent 给了看似合理的回复”替代真实工具记录与健康验证。

## 7. 分阶段发布门槛

| 阶段 | 对用户交付 | 完成门槛 |
|---|---|---|
| 内部纵向原型 | 一项目、一会话、两专员、一个资源列表入口和一个内嵌终端 | 全部六步在测试环境中可演示；资源详情可进入会话终端，刷新恢复、用户接管与拒绝审批可复现 |
| Web 私测版 | 项目和会话管理、服务端持久状态、可观察的并行调查、受限 L2 操作 | 用户可在真实非生产环境独立完成一次排障；断线、超时、重复点击和并发输入不产生重复操作；发布已知限制 |
| Web 公测候选 | 部署和备份文档、权限与审计、故障样本评估及回归 | 对选定故障集合记录检索到的关键证据、错误假设、操作参数正确性、误操作/拒绝行为和人工反馈；完成权限/凭据边界检查 |
| 桌面客户端 | 复用 Web 会话协议与 Agent 服务，增加系统桌面集成 | Web 行为与会话数据在桌面端一致；另行验证客户端打包、签名和升级 |

评估集从真实或脱敏故障轨迹与合成故障构造：先以专家核验的少量 Gold 样本校准，再加入程序可验证的 Silver 和启发式 Bronze 样本；调查质量、引用证据、工具使用及最终操作参数分别评估。L3/L4 不由首版路线图自动开启，必须针对具体动作有独立的评估数据和风险控制证据。

## 8. 近期决策与下一步

先做**产品原型验证**，而不是同时搭完整资源中心、自动修复平台和桌面客户端。原型只选一个代表性故障、两个专员和一个内嵌终端。原型完成后根据实际使用决定：项目是否需要更多资源管理、专员划分是否有效、审批粒度是否太重、Web 私测所需的身份和部署方式。旧代码的可复用部分在这些需求稳定后逐模块评估。

本方案的开源选型以 2026-10-10 的项目公开文档为依据。引入代码时保留各自许可证文本，确认打包的依赖与资产许可；正式发布前再次核对版本和接口。
